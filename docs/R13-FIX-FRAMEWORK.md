# Relay Fix Implementation Framework

Prepared October 22 2026 for John and the implementing team

This framework is the acceptance specification for repairs to findings F1 through F7 and the watcher 38 closure criteria. Implement each work package behind the team's review gate. Start with F4's narrow diagnostic-retention repair, then establish shared action contracts before changing deadlines, execution guards, or receipt classification. Watcher repair can proceed independently and remains the highest operational priority in the reported workflow.

The source baseline is public R12 commit `ee3cf0e2dbc4bd2b2cac3ee1651471aa41a6dbd1` in ADD-Attack/muse-relay-v2. All existing file and function names below were checked against that checkout. Proposed helpers, protocol fields, and states are explicitly described as new. Line numbers are baseline navigation aids and will move during implementation. Existing R4 or R7 comments that also use finding numbers are historical identifiers, not this review's F1 through F7.

Local simulations support the findings; packaged Windows behavior remains **UNVERIFIED**. The external watcher scripts and their deployment environment were not supplied. Their reported defects are handoff evidence, and watcher function names cannot yet be verified. This specification does not authorize deployment or replay of uncertain actions.

## Delivery and acceptance boundaries

The accompanying `test_relay_fix_acceptance.py` converts the original 13 probes into desired-behavior tests. Parameterization adds malformed-response variants, independent focus and owner changes, and healthy controls, for 21 collected checks. On unchanged R12, 18 failed and 3 passed. These failures are the expected repair backlog; they are not a passing product certification. The controls prove that the existing countdown decreases and that ordinary nonjitter typing and resting motion still work in the simulated healthy case.

Run the test file in its own Python process with `RELAY_REPO_ROOT` pointing to the candidate checkout. It uses Flask clients and fake desktop/network boundaries. Install the candidate's dependencies plus pytest and Pillow in an isolated environment. Do not execute it alongside production hands. The original read-only reproduction script is included for provenance; it asserts the old defective behavior and is not an acceptance gate.

The executable tests are a starting gate, not the entire closure specification. Each finding also has mandatory integration, fault-injection, or Windows criteria below. Tests using new protocol or backend seams must be ported with those seams; changing an adapter is allowed, weakening the stimulus or expected outcome is not. No xfail, unconditional skip, sleep-based race lottery, or always-disabled feature counts as a repair.

Receipt semantics must separate three facts: whether dispatch occurred, what hands reports about input injection, and whether the target application achieved its intended effect. `applied` means a valid hands response confirms completion of the requested injection routine. It does not mean a save succeeded, logging started, a dialog closed, or typed text was accepted by the application. Partial character counts describe injection calls completed, not verified document contents.

## Shared contracts to settle before implementation

**Action start and expiry.** A queued action has one immutable start deadline. The deadline constrains the first side effect, including pointer movement or clipboard mutation, rather than the HTTP request or acquisition of a mutex. Equality is expired. Once input starts, expiry alone does not cancel the action midway; owner, lock, and target guards still apply. Releases of buttons or modifiers already pressed are cleanup and must run even after expiry or abort.

Use monotonic time for local decisions and wall time only for display. Preserve the public held deadline as a hold interval beginning when the first no-effect yield response reaches the gateway. Add a proposed authenticated hands execution-lease endpoint before the first queued attempt. It mints an opaque lease with a bounded lifetime no greater than hold_seconds on hands' own monotonic clock, a hands boot identity, and an immutable operation identity/digest. Minting a lease has no desktop side effect. The gateway retains that same lease across no-effect yields; it must never obtain a fresh lease automatically after expiry, partial execution, or uncertainty.

Hands checks its own lease under input access immediately before the first side effect and atomically marks it started. A started lease cannot inject again. Because the lease was minted before the first yield response reaches the gateway, its expiry is no later than the end of the public hold interval. No comparison of unrelated monotonic clocks is required. Lease expiry can shorten the usable hold, so expose both local queue state and hands refusal reason. Do not claim this provides a client-submission deadline or a durable exactly-once guarantee. A separate end-to-end deadline would require its own reviewed clock/transport contract.

Add versioned capability negotiation before enabling protected queues. Strip caller-supplied internal lease metadata at the gateway. Hands rejects unknown, consumed, changed-operation, wrong-boot, expired, and nonfinite/invalid lease requests. Keep digests internal; a digest of short private text is not safe public receipt content. Old or incompatible hands receives no protected queued attempt and produces a definite capability refusal. A relative TTL restarted on every retry is not a lease. A lease has an immutable receiver-local expiry.

Preserve unrelated contracts: valid credentials still bypass authentication lockout; claims remain advisory; claim TTL default/minimum/maximum remain 900/30/3600 seconds; reservation grace remains 30 seconds; hold bounds remain 1 through 120 seconds. Keep R12 motion planners, authentication, capture parameter validation, payload privacy, and cleanup releases. A refused action that never started must not reset the resting-hand ramp or clear its owner-stop state.

**Action outcomes.** Introduce one classifier, proposed as `classify_act_outcome`, shared by the initial queued attempt and retry settlement. Inputs include transport certainty, HTTP status, a validated body, and whether an injection attempt may have begun. The following table is the required policy; helper names may change.

| Evidence | Receipt state | Retry policy |
| --- | --- | --- |
| Valid complete success body and successful HTTP status | applied | Terminal |
| Verified owner or locked refusal before any side effect, with a target and time budget | held | Retry only within the original deadline |
| Deadline reached before dispatch or hands proves no start before expiry | refused-yielded with reason deadline_expired | Terminal |
| Valid known refusal or operation failure | failed with execution evidence retained | Terminal; never infer zero partial effects from the label alone |
| Valid owner abort with a known partial count | aborted-owner | Terminal |
| Valid lock or foreground abort after input starts | aborted | Terminal, with reason and partial evidence |
| Response lost, invalid success body, contradictory success evidence, or exception after possible dispatch | unknown-outcome | Terminal for automatic processing; never replay |
| Receipt absent or evicted | unavailable in the lookup response | Never interpret absence as proof of nonexecution |

During the narrow F4 stage, `failed` plus preserved abort diagnostics is acceptable. After the F3 state work, owner aborts must use `aborted-owner`. Existing `expired` may remain for retention eviction, but the API must distinguish record unavailability from an action that provably never started. Introducing a new state also requires clients and UI to handle it without mapping it to success or offering an automatic retry.

**Result privacy.** Keep request payload values out of receipts, persistence, and logs. Retain bounded, typed diagnostic fields through an allowlist: outcome/error code, abort reason, guard mode, method, boolean abort flag, total and completed injection counts, and validated timing metrics where useful. Use controlled codes and generic messages instead of arbitrary exception text, debug objects, or upstream strings that can echo typed text. Copy values into a fresh object. Check numeric types, finiteness, nonnegative bounds, and `chars_typed <= chars`; reject contradictory counts rather than fabricating a prefix length. Counters must accommodate the supported input limit, not an unexplained lower cap.

## F1 Held actions start after their deadline

**Root cause.** `services/gateway/app.py:_pump_receipt` forwards a held operation before checking its deadline and checks expiration only if the result is another yield. It also uses the supplied `now` for settlement after a potentially slow forward. `_receipt_loop` already samples time per receipt, so the defect is not a single timestamp cached across the whole sweep. An additional deadline check in the gateway cannot stop an operation that waits inside hands for input access or attention delays and begins after its start window.

**Change points.** In `services/gateway/app.py`, change `_pump_receipt` at line 1123, `_receipt_loop` at 1176, `_forward_act` at 1199, and `act_queued` at 1310. Audit `_store_receipt` at 1093 for concurrent eviction. In `hands/muse_relay_hands.py`, change `_input.__enter__` at 665 and the first-side-effect paths in `move`, `click`, `type_text`, `key`, `scroll`, `hotkey`, `break_`, `drag`, `focus`, and `clipboard_set`. `hands/motion.py:InputMutex.acquire` at 547 includes a hand-travel sleep and must not be treated as an immediate acquisition. Add the proposed hands execution-lease endpoint/store and a shared hands guard method for checking the lease immediately before the first side effect and after any preparatory wait.

**Required behavior and invariants.** Reject an expired receipt under the receipt lock before reserving its dispatch. Atomically reserve a held receipt for one attempt, then release the receipt lock before network I/O. A second pump cannot send the same pending attempt. Concurrent eviction must not cause a dispatched result to be published as a definite never-started expiration. Do not hold the global receipt lock while waiting on hands. Preserve the original immutable deadline through all retries; successful input that starts before it may finish later. Invalid or nonfinite timing fields fail closed before side effects. Once terminal, remove the transient payload and prevent future pump calls from dispatching it.

**Acceptance.** P01 in the executable suite covers equality and already-expired dispatch. F1-A adds two receipts: the first forward advances a fake clock beyond the second's deadline; the second must have zero forwards. F1-B acquires the hands mutex only after the deadline and asserts zero movement, key, click, focus, or clipboard calls. F1-C advances time during hand travel and during click attention/hover; expiry before the first side effect prevents all input. If approach movement already began on time, later deadline crossing is not a never-started expiry. F1-D starts two pump threads at a barrier and observes exactly one attempt; simulate eviction while the response is outstanding and preserve execution uncertainty. F1-E tests wall-clock jumps, mismatched boot identities, altered operation digests, consumed leases, invalid lifetimes, network delay, independently offset clocks, and old hands capability. F1-F confirms a valid start just before the deadline can complete normally and that modifier/button cleanup still executes.

## F2 Execution checks become stale while waiting

**Root cause.** The hands `gate` runs owner and foreground checks before routes acquire `_INPUT`; subsequent waits permit the owner or foreground to change. Checks can also become stale during attention delays inside the mutex. Locked-desktop responses omit a foreground handle, so the gateway can hold an operation with no target. An input mutex serializes relay operations but cannot freeze the physical owner or the Windows foreground. `focus` and `clipboard_set` currently bypass `_input` entirely, so changing its context manager alone leaves side-effect routes uncovered.

**Change points.** In `hands/muse_relay_hands.py`, change `gate` at 396, `_yield_if_active` at 236, `_focus_guard` at 336, `_input` at 659, and the same side-effect routes listed for F1; include `_run_path` at 693 for multistep execution. In the gateway, change `act_queued` target capture and retry metadata. Extend the existing tests for focus, queued acts, and input serialization. Proposed guard exceptions and their Flask response handler are new code; an exception raised by `__enter__` must release the lock because `__exit__` will not be called.

**Required behavior and invariants.** Keep the early authentication gate, then revalidate owner, lock state, expected target, and execution lease under input access immediately before a side effect. Check again after preparatory waits. Owner activity detected before injection can yield; a changed or unknown required target is terminal. During a multistep operation, recheck at each defined injection boundary and return partial-abort evidence, never a replayable yield after any side effect. Cleanup releases are exempt from target checks.

For a held foreground-sensitive act without an explicit expectation, capture a trustworthy target on the first no-effect refusal. Reject `locked` holds with `target_unknown` when no trustworthy target can be established; never pin whatever window happens to be foreground after unlock. A valid caller expectation is preserved and checked. `focus` has a distinct intended target and must re-enumerate/validate the selected window under input access rather than insist that it is already foreground. `clipboard_set` needs serialization and owner/lock/deadline checks but does not need automatic foreground pinning. Target identity should include a process lifetime or equivalent protection against handle reuse where available. A bare HWND cannot prove identity across destruction and reuse.

**Acceptance.** P06 asserts an unpinned locked click does not remain replayable. P07 separately changes only owner state, only foreground state, and both during acquisition; each case requires HTTP 409 and zero injections. Its lock-release probe uses another thread because reacquiring an RLock on the same thread would conceal a leak. F2-A repeats the race during attention sleep and before click-down following approach motion, checking the correct no-start or partial-abort result. F2-B repeats across every route named above and across human/direct branches. F2-C covers locked-with-explicit-target, unknown foreground, mismatched process, destroyed/reused handle, and `focus` target disappearance. F2-D performs a valid same-target action afterward to prove the fix did not disable input. F2-E uses a Windows test window that deliberately changes foreground between steps; bound the test to observed guard checkpoints and never claim OS-atomic focus-plus-input.

## F3 Receipt states overstate execution certainty

**Root cause.** `_forward_act` converts requests failures to a generic 502 and synthesizes `ok:true` from an empty or invalid successful body. `act_queued` and `_pump_receipt` classify success from HTTP status alone. As a result, a timeout after real dispatch becomes `failed`, while HTTP 200 with no valid confirmation or `ok:false` can become `applied`. Receipt creation after the initial dispatch and in-memory retention also limit lost-response and restart recovery; those limitations must not be presented as proof that an action did not run.

**Change points.** Change gateway `_forward_act`, `act`, `act_queued`, `_pump_receipt`, `_public_receipt`, `act_queued_get`, and `act_queued_list`. Add the proposed outcome classifier and typed safe-result normalizer. Create an in-flight receipt identity before initial dispatch. In `muse_relay_v2_app.py`, audit `_snapshot_receipt_rows`, `summarize_receipts`, `receipt_state_counts`, and `build_dashboard_model`. In `ui/app.js`, extend `STATE_CHIP`, `STATE_COLOR`, and `renderFeed` for unknown and abort states. Check diagnostics formatting and README API examples. No hands success schema should be silently strengthened beyond what the implementation can actually observe.

**Required behavior and invariants.** Require a JSON object with a boolean `ok` and a recognized outcome contract. A successful status and valid `ok:true` are necessary for `applied`; missing, string-valued, nonobject, contradictory, or malformed evidence is unknown after possible dispatch. An explicit valid `ok:false` is never applied. A known pre-dispatch configuration, validation, authentication, or protocol refusal may be failed without claiming partial effects. A read timeout, generic connection failure, or unexpected exception after the send boundary is unknown unless the transport proves no request could have reached hands. Do not classify every `ConnectionError` as a definite no-send.

Both direct and queued APIs must tell the same truth. Return 502 and `ok:false` for transport uncertainty or an invalid success body, attach the receipt ID for queued calls, and preserve a stable machine-readable uncertainty code. Only verified no-effect yield/locked responses are retryable. Old prose matching must not classify a partial abort as a yield. The input text must never be reconstructed or automatically resubmitted from a partial count. UI displays unknown and abort states distinctly, with no green success and no blind replay action.

**Acceptance.** P02 simulates one dispatch followed by ReadTimeout, then pumps again and requires one total send and `unknown-outcome`. P03 checks empty, array, null, string, and missing-ok successful bodies; all must return 502 without applied. P05 checks HTTP 200 with `ok:false`. F3-A runs these cases through both immediate and held paths, and includes ok values of `1`, `"true"`, and null, HTTP 500 with `ok:true`, and valid owner/locked refusals carrying contradictory partial counts. F3-B verifies known configuration rejection does not send. F3-C verifies status polling, list views, UI colors/text, and diagnostics preserve all new states. F3-D asserts payload deletion and zero retries after partial or uncertain results, including a second pump and a retry-thread restart. F3-E evicts a known receipt and verifies lookup reports unavailable, never provably unexecuted.

**Separate crash-recovery gate.** Core F3 closure fixes response classification; it does not claim durable recovery. To advertise recovery across gateway/power loss, add a client-generated request ID, a durable pre-dispatch attempt record, payload-hash collision rejection, and a hands deduplication/reconciliation contract. Persist no sensitive payload by default. A crash after send and before the result commit recovers as unknown, with no automatic replay. An idempotency key in the gateway alone cannot provide exactly-once desktop effects across a crash. Treat this as a separate reviewed package with process-kill tests before send, after send, after input, and before/after result persistence. Until it passes, document receipt retention and missing-history ambiguity explicitly.

## F4 Held failures lose partial execution details

**Root cause.** The held failure branch in `_pump_receipt` sets `receipt["result"] = None`, discarding the hands response. Immediate failures retain the response. An owner-aborted type can therefore report a count at the HTTP boundary but lose it when the caller polls its held receipt. Changing the GUI label does not recover the missing prefix count and copying the whole body would risk persisting echoed text or debug data.

**Change points.** Change `services/gateway/app.py:_pump_receipt` at 1164 and add a bounded diagnostic extractor immediately before it. Reuse the extractor in the broader F3 normalization work; audit `_public_receipt` and the direct settlement path. The bonus patch adds a proposed `_held_failure_diagnostics` helper and tests in `tests/test_f4_diagnostics_reference.py`. The UI state change belongs to F3 and wishlist 35, not this minimum F4 patch.

**Required behavior and invariants.** Retain recognized `error_code`, `abort_reason`, `owner_guard`, `method_used`, `aborted`, `chars`, and `chars_typed` in a fresh safe result object. Keep a partial abort terminal and remove its pending payload. Preserve the supplied HTTP status and distinguish a genuine zero count from missing count evidence. Do not reuse a mutable upstream object. Preserve privacy by excluding request text, arbitrary error prose, and nested debug structures. Existing successful receipts and hold classification remain compatible during this narrow stage.

**Acceptance.** P04 supplies an owner abort after 12 of 40 characters with a private sentinel in text/error/debug fields. Polling must retain the count and reason, omit the sentinel, delete pending input, and resist later mutation of the source dict. F4-A exercises owner and lock aborts, known zero, missing count, wrong types, huge or negative counts, and `chars_typed > chars`. F4-B pumps the result twice and observes exactly one forward. F4-C tests direct/held diagnostic parity after F3 normalization. The isolated reference patch passes its four local tests and P04, but it does not implement cross-field count validation, new abort states, all direct-path sanitization, or F3 uncertainty. It remains **UNVERIFIED** for production and Windows; it is a narrow starting patch, not full finding closure.

## F5 Owner input protection has bypasses

**Root cause.** The jittered key path creates `_TypeOwnerGuard`, while nonjitter bulk write and paste bypass it. Ordinary agent input is not consistently represented in the owner-idle mechanism. Resting motion treats a broad time interval as self-input, so a physical keyboard event inside that interval can be hidden even while the cursor remains where the glide expects it. Existing hook counters can distinguish hardware events from injected events, but are not yet used consistently across these paths. Injection flags identify injected events generally, not uniquely this relay.

**Change points.** In hands, change `_yield_if_active`, `_input`, `type_text` and its `_keys`/`_paste` closures, `_type_dispatch`, `_TypeOwnerGuard`, `_OwnerInputMonitor`, `_RestingHand.step`, and `_RestingHand._move`. Audit `_run_path`, click/drag button pairs, scroll chunks, key/hotkey/break, focus, and clipboard mutation. In `hands/motion.py`, change `SelfInputLedger.owner_idle`, `_is_self`, and `owner_input_since` or remove their use as authoritative owner discrimination. Preserve the repaired `_move` finally cleanup and the existing motion planners.

**Required behavior and invariants.** Use a shared owner observation service with a persistent physical-event counter and last-owner monotonic time. A new action must check recent owner activity against the configured threshold, not merely snapshot a fresh counter and forget earlier physical activity. Healthy hooks take precedence over timestamp spans. Detect hook death or deafness and report degraded coverage. Conservative fallback may yield unnecessarily; it must not assert reliable owner discrimination. Disable optional resting motion when reliable physical-input observation is unavailable. Keep foreground/lock safety independent of provenance mode.

Use the same bounded key loop for jitter true and false; jitter changes delays only. Define an injection unit as one character, one pointer step, one scroll chunk, or one discrete key/chord. Sample owner/lock/focus before each unit. After a detected owner event, emit no new units; an already-running native primitive and required key/button-up cleanup are the documented bound. This is a deterministic call-boundary contract, not a claim of zero milliseconds of physical latency. A hook event delivered while the current unit runs must stop the next unit.

Paste must sample immediately before clipboard mutation and again before Ctrl+V. If owner activity occurs before the chord, do not paste. Restore the saved clipboard only if the clipboard still contains the value/version placed by this operation; never overwrite a newer owner clipboard value. Once the paste chord may have been sent, an exception cannot fall back to typing the whole payload. `_type_dispatch` currently catches every paste exception; replace that broad fallback with an explicit pre-injection-unavailable condition. Report paste injection and any uncertainty honestly; do not manufacture `chars_typed` for application consumption. Support simultaneous owner and injected events, including the same OS tick. For third-party injected input, expose the coverage limitation or add relay-specific event tagging before claiming attribution to this relay.

**Acceptance.** P11 injects a physical keyboard event during a resting step's sleep with no pointer displacement; exactly the first step executes and the rest stops. Its paired control reaches the target with multiple steps. P12 uses nonjitter keys: a physical event during the first write must stop the remaining loop with an accurate count; the no-owner control emits all 130 characters. F5-A repeats owner takeover on every route and human/direct branch, including event-before-first-unit and same-tick owner plus injected events. F5-B runs rapid successive ordinary acts without physical input and requires no self-yield; adding recent physical input must yield. F5-C tests hook death/deafness and requires explicit degraded guard status and stopped resting motion. F5-D injects clipboard read/set/chord/restore failures and owner changes between them; require no duplicate typing fallback after possible paste and no restoration over owner content. F5-E aborts drag and chords and asserts every pressed button/modifier is released. F5-F tests 32-bit tick rollover, late input publication, and mid-glide exceptions without reopening the already-fixed provisional-span leak.

## F6 Gateway restart breaks claim synchronization

**Root cause.** The gateway process initializes `_claim_push_seq` to zero, while a surviving `_RestingHand` retains its accepted sequence. New grant or release pushes can be rejected until the counter catches up. Pushes run independently on threads and their failures and rejection bodies are ignored. Remaining lease duration is calculated before delivery and added to hands time on receipt, so delayed delivery can also extend a lease. A random process UUID distinguishes processes but does not order them; accepting every unseen UUID permits a delayed old process to regain authority.

**Change points.** In the gateway, change `_claim_push_seq` initialization, `_post_claim_to_hands` at 103, `_push_claim_locked` at 112, `_current_claim_locked`, `hands_claim`, and `hands_release`. In hands, change `_RestingHand.set_claim` at 1517, `claim_held`, `status`, and `resting_claim` at 1698; expose hands boot identity through a capability/status response. Integrate startup and shutdown in `muse_relay_v2_app.py:RelayApp._start_one_locked` and `stop`. Persistent synchronization metadata and its storage helper are new files; choose and document their packaging/configuration location in the implementation PR.

**Recommended protocol.** Use one configured authoritative gateway for each hands pairing. Acquire an exclusive gateway process lock, atomically allocate and durably store a monotonically increasing integer epoch before serving claim traffic, and start a sequence within that epoch. Do not use random UUID ordering or wall time as an epoch. Include pairing ID, gateway epoch, sequence, hands boot ID, stable claim ID, and a single-use receiver-issued timing challenge. Hands validates authentication, pairing, boot ID, and epoch/sequence. Persist a newly accepted epoch before enabling motion; sequence ordering can be volatile within the current hands boot because every message is bound to that boot. Persistence failure leaves resting motion disabled and surfaces synchronization error. A new hands boot clears all active grants, changes boot ID, and requires a current snapshot; old boot messages cannot revive them.

A proposed hands challenge endpoint records its issuance time on hands' monotonic clock. The gateway obtains the challenge, then reads a fresh authoritative claim snapshot and computes remaining duration from its own monotonic lease. Hands applies an effective permit expiry no later than challenge-issuance time plus that duration, additionally capped by a short receiver-local synchronization permit. This anchors expiry before network delay. Reject reused, wrong-boot, and expired challenges. The proposed default permit is two seconds, refreshed every half second while healthy; test those explicit values and make any measured adjustment a reviewed configuration change. This short permit bounds optional resting motion during a disconnection; it does not change the 900/30/3600-second advisory claim lease. Keep wall-time expires_at as a public display projection of the authoritative monotonic lease.

Use one reconciliation worker instead of an unbounded thread per push. Coalesce to the latest state; validate ok, applied, boot, epoch, sequence, and claim identity in acknowledgements. Retry the latest snapshot with capped backoff while exposing synchronization health. Startup must explicitly reconcile an absent claim as a release. An identical already-accepted message can be acknowledged idempotently but cannot extend its permit. A new synchronization refresh needs a fresh challenge and higher sequence. Release supersedes every older grant; lower epochs or lower same-epoch sequences are rejected. Loss or rollback of the epoch store requires explicit pairing recovery while motion is disabled, never silently resetting to zero.

Give each actual claim grant a stable identity that survives renewal. Same-claim synchronization must not reset the resting ramp or clear owner-stop state, including after a temporary synchronization gap. Only the documented new-claim or real-act transition may rearm it. Permit loss/release must be checked during an in-progress glide before the next planned substep, not only at the next outer resting decision. This depends on F5's guard boundaries. Claims remain advisory coordination, not authentication for ordinary actions.

**Acceptance.** P09 bridges a gateway instance and a restarted instance to the same hands object; the new release must clear the old grant. Port the fixture to use a temporary epoch store and an explicit lifecycle transition when the new protocol is added; importing twice is only the R12 reproduction seam. F6-A accepts epoch 8/sequence 7 held, accepts epoch 9/sequence 1 release, then delivers delayed epoch 8/sequence 100 and asserts released. F6-B delivers duplicate grants and stale releases and checks both state and unchanged permit deadline. F6-C delays a grant beyond its original lease and requires no activation. F6-D drops the first release, returns HTTP 200 with applied false, restarts hands, and verifies reconciliation reaches the latest state within the configured retry bound; when the link stays down, resting motion stops within the two-second permit plus the next guarded injection boundary. F6-E uses two actual processes against the same epoch file: only one acquires the authority lock; a killed process permits its successor to allocate a larger epoch. F6-F crashes around epoch persistence and hands epoch persistence, injects disk failure and restored old files, and requires fail-closed synchronization. F6-G confirms claim FIFO/reservations, normal renewal, lazy expiry, owner-stop state, ramp timing, and valid-token input behavior remain intact. Test same-claim reconnect and release during a glide.

## F7 Secondary monitor capture uses the wrong surface

**Root cause.** `_grab` assumes PyAutoGUI's ordinary screenshot is a virtual-desktop image and supplies regions in global desktop coordinates. The reviewed upstream Windows capture defaults to the primary surface, then crops it. Under those semantics, right-side or negative-origin secondary regions become black padding. Merely turning on all-screens capture is also insufficient when the returned bitmap starts at the virtual desktop's negative origin; crop coordinates need translation. The exact dependencies in the deployed executable remain unverified.

**Change points.** Change `hands/muse_relay_hands.py:_grab` at 511 and `screenshot` at 542; validate `_monitor_rects` at 467 and `_parse_region` at 524. Add a proposed capture backend seam returning pixels plus the global origin and extent of those pixels. In the gateway, audit `_fetch_screenshot`, `_screen_fetch_kwargs`, `screen`, `screen_hash`, and `screen_wait` for preserved capture-variant metadata and hashing. Update `build_app.bat` and `hands/build_muse_relay.bat` to package the selected backend. The existing `services/gateway/requirements.txt` covers gateway dependencies; add a new explicitly named hands/build lockfile if needed because this baseline has no hands requirements manifest. Do not assume PyAutoGUI passes all-screen flags through every packaged version.

**Required behavior and invariants.** Establish a documented coordinate space and DPI-awareness mode. With virtual origin `(vx, vy)`, crop a requested global `(x, y, w, h)` using `(x-vx, y-vy, x-vx+w, y-vy+h)`. Validate dimensions and bounds; reject out-of-surface regions rather than returning fabricated black padding. Preserve the legacy default capture extent unless a versioned capability explicitly changes it. Capture selection and metadata must refer to the same monitor topology snapshot, or detect a topology change and retry/refuse. Monitor array order is not a permanent display identity. Hash and conditional requests must refer to the same variant and not reuse a primary-screen cache for another region. Preserve authentication and PNG response behavior.

**Acceptance.** P13 uses a red primary, green left display at x=-100, and blue right display at x=100. It asserts actual pixels, not just dimensions. Port its fake backend at the new capture seam if Windows-only selection is moved behind an adapter; do not accept a test that accidentally exercises a Linux fallback. F7-A adds negative y, nonzero virtual origin, mixed sizes, primary not at index zero, regions crossing displays, invalid/out-of-bounds regions, and hot-plug during enumeration/capture. F7-B exercises PNG routes, hash/wait, variant headers, and conditional ETags against that geometry. F7-C captures known patterns on the exact Windows packaged build at 100/125/150 percent scaling, maps a known safe test-window point through screenshot coordinates, and verifies the input target agrees. Record dependency versions, executable hash, topology, DPI mode, and resulting image dimensions. Simulation alone cannot close this packaged-runtime gate.

## Watcher 38 Closure Criteria

**Root cause from the handoff.** Both external watcher variants reportedly permit duplicate instances, share temporary filenames, swallow fetch failures, and present stale files as if they prove ongoing observation. Relay watcher registration is refreshed before screen acquisition succeeds, so contact can appear current while observation is failing. ALIVE logs prove process progress only, and identical frame hashes prove content equality only. Neither establishes fresh screen capture or that TunerStudio is actually logging.

**Verified relay change points.** In `services/gateway/app.py`, change `_touch_watcher`, `_current_watchers`, `watch_touch`, `screen`, `screen_hash`, and `screen_wait`; audit `_fetch_screenshot` validation. In `muse_relay_v2_app.py`, extend `_watchers_or_empty`, `build_dashboard_model`, and diagnostics; update `ui/app.js:renderClaim` to distinguish contact from observation. The external laptop watcher is named `watch-live-laptop.py` in the packet; its path and functions and the Abraham variant's identity are unverified. Before implementation, the owner must map six responsibilities to real symbols: instance lock, fetch/decode, publication, heartbeat, failure logging, and consumer freshness check. **Required behavior.** Enforce one process owner per target/output set using an OS-held lock or equivalent robust lifetime lock. A plain stale PID file check is insufficient. Second launch exits nonzero with a visible explanation. Use unique temporary files even with the lock. Publish a complete generation of full image, display image, and metadata, then atomically replace one manifest/pointer to that generation. Separate renames of three shared files are not an atomic snapshot. Readers resolve one generation and never mix image and timestamp versions. Cleanup must not remove files still referenced by the published manifest.

Track distinct `last_attempt_at`, `last_success_at`, `last_published_at`, `process_heartbeat_at`, content-change time, consecutive failures, and last error code. Define gateway success as a newly validated capture response; it is not proof of client publication. P08's additive relay fields are `last_success_at` and `last_fetch_ok`, with existing `last_seen` retained as contact time. Never let a heartbeat or explicit watch registration advance successful-fetch time. A static successful capture may advance success and observation generation without changing the content hash. An error never advances success or publication time.

For each watcher configure poll interval P, request deadline T, and stale threshold S in seconds; require finite positive values and set S explicitly. Acceptance fixtures use P=3, T=5, S=10. Show error immediately on fetch/decode/publication failure and stale when monotonic age since last validated success is at least S. Show unknown on startup or incompatible time metadata. A paused watcher is visibly paused, never fresh. A heartbeat cannot override error/stale. Conditional 304 counts as a fresh observation only when the protocol proves a new capture was validated for that response; otherwise force a full fetch. In R12 `screen` fetches before checking ETag, but proxy caching still needs validation in the deployed path.

**Acceptance.** W01 starts two real watcher processes on the same output set; exactly one retains the lock, the loser reports an error, and kill/relaunch recovers ownership without deleting another process's lock. W02 bypasses the lock in a fault-injection build, forces identical publication schedules, and proves unique temporary names prevent corruption; readers still see only complete generations. W03 kills the publisher after each write and rename; readers see the previous complete generation or the next complete generation, never mixed content. W04 alternates success, HTTP 502, timeout, invalid PNG, and disk-full publication failure; check every timestamp and error counter. P08 covers the relay subset of W04.

W05 returns identical pixels successfully for 30 seconds: observation timestamps advance, content-change time stays fixed, and the process remains fresh. Then fail fetches while heartbeats continue: error appears immediately and stale is true by age S. W06 tests clock jumps, process restart, generation-counter reset, stale manifest, and two consumers. W07 pauses/resumes and tests each watcher variant under its actual launch/supervision mechanism. W08 records two validated observations separated by a configured interval and fresh application-specific evidence that logging is active or its output advances; a live screenshot of a closed dialog alone is insufficient. This is a workflow acceptance check, not a claim that a screenshot can prove every application effect. ## Challenge pass and resolved objections

The second pass challenged the draft against source and test behavior. The following corrections are incorporated into this version.

1. **A gateway-only expiry test was too weak.** The spec now defines first side effect, equality, after-wait checks, receiver-local execution leases, old-hands behavior, and safe cleanup. The serial loop already takes a fresh wall-time sample per receipt; the root-cause paragraph no longer misstates that detail.
2. **Changing the context manager did not cover every route.** `focus` and `clipboard_set` bypass it in R12. Both are named explicitly, and exception handling must account for failed `__enter__` not invoking `__exit__`.
3. **The original lock-release assertion could pass with a leaked lock.** InputMutex uses RLock. The executable P07 now checks acquisition on another thread, and independently tests focus and owner changes so one repaired guard cannot mask the other.
4. **A feature that always refuses input could pass negative tests.** Paired healthy P11/P12 controls require real simulated progress and successful completion. P11 also requires the first step to occur before the injected owner event.
5. **Copying arbitrary failure JSON would preserve secrets as well as diagnostics.** F4 now specifies typed, bounded copying and sentinel tests. The bonus patch's missing cross-field validation is explicitly retained as a production limitation, not silently called complete.
6. **Unknown was underspecified.** F3 now distinguishes definite local rejection, valid failure, partial abort, and ambiguous transport; no HTTP-only success, no generic connection-error certainty, and no replay after uncertainty. Durable recovery is a separate gate with its own dependencies.
7. **A new UUID could admit a delayed old gateway.** F6 now requires ordered persisted epochs, single authority, restart boot binding, receiver-timed permit challenges, validated acknowledgements, and reconciliation. Release during a glide adds an explicit dependency on F5. P09 alone cannot prove all of those; F6-A through G are mandatory.
8. **Paste exceptions could duplicate text.** F5 explicitly narrows fallback to pre-injection unavailability and tests faults after the chord. Clipboard restoration must not overwrite newer owner data.
9. **All-screens capture still needed origin translation.** F7 tests pixel colors with negative origins and requires DPI, topology and packaged-backend checks. The fake backend is an adapter seam, not proof of Windows execution.
10. **Three atomic renames did not make one atomic observation.** Watcher closure now publishes immutable generations through one manifest and tests process death at each publication stage. Heartbeat, static content, successful observation, and application effect have separate evidence.

Remaining limitations are explicit: no exact watcher function map without scripts; no packaged Windows acceptance; no OS-atomic guarantee between a guard read and native input; no exactly-once desktop effects from an in-memory receipt; and no runtime attestation of the requested High/Max effort selector. The drafting and challenge passes are recorded by their work and results, not by an unverified model-setting claim.
